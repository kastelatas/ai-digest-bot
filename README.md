# AI/IT-дайджест бот для Telegram

Полуавтоматический пайплайн для канала: собирает новости из RSS, пишет черновик
поста через LLM (OpenRouter или Claude), присылает вам на одобрение кнопками в Telegram, публикует
по расписанию, ведёт мини-CRM по рекламе и считает недельный отчёт.

Специально **не** публикует посты без вашего одобрения — это осознанное
решение, а не недоделка: полностью автоматическая публикация без проверки
человеком быстро приводит к фактическим ошибкам и репутационным потерям
(модель может неверно понять источник, даже с защитой от «мусорного вывода»
в промпте). Вы одобряете/отклоняете черновик одной кнопкой — это занимает
секунды, а не рабочий день.

## Быстрый старт

Разворачивается на любом VPS с Python 3.11+ (Ubuntu/Debian — самый простой
вариант). **Не пытайтесь запускать это внутри среды, где вы сейчас читаете
этот текст** — если это песочница ассистента, у неё нет доступа к
api.telegram.org и обычным сайтам, только к реестрам пакетов и GitHub.

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt

cp config.example.yaml config.yaml   # отредактируйте под себя
cp .env.example .env                  # впишите токены
```

В `.env`:
- `TELEGRAM_BOT_TOKEN` — токен от [@BotFather](https://t.me/BotFather). Бота
  нужно добавить админом и в канал (публиковать посты), и в админ-чат
  (личку с ботом или закрытую группу — присылать черновики на одобрение).
- `OPENROUTER_API_KEY` — ключ с [openrouter.ai/keys](https://openrouter.ai/keys)
  (провайдер по умолчанию, `llm.provider: "openrouter"`). Или `ANTHROPIC_API_KEY`
  с [console.anthropic.com](https://console.anthropic.com), если выбран
  `llm.provider: "anthropic"` — нужен ключ только выбранного провайдера.
  Без ключа `fetch` работает в офлайн-демо-режиме (просто обрезает текст
  источника, публиковать такое в канал не стоит).

В `config.yaml`:
- `llm.provider` и `llm.model` — для OpenRouter модель пишется как «вендор/модель»
  ([каталог](https://openrouter.ai/models)). По умолчанию `google/gemini-3.1-flash-lite`
  (дёшево, хороший русский); бесплатный вариант с лимитами — `google/gemma-4-31b-it:free`.
  Своя OpenAI-совместимая точка — `llm.base_url`.
- `channel.chat_id` — `@username` канала или числовой id для приватного.
- `admin.chat_id` и `admin.allowed_user_ids` — куда слать черновики и кто
  имеет право их одобрять (проверяется по `from.id` в нажатии кнопки).
- `sources` — список RSS-лент. В примере уже 6 проверенных на момент
  сборки источников (TechCrunch AI, OpenAI News, MIT Technology Review,
  Hacker News, Habr — ИИ и Разработка). Добавляйте свои.

## Как запускать: cron, а не демон

Пайплайн рассчитан на короткие запуски по расписанию, а не на вечно висящий
процесс — так проще перезапускать после сбоя и не нужен systemd для базового
сценария. Пример `crontab -e`:

```cron
# собрать новости и разослать черновики на одобрение — каждые 30 минут
*/30 * * * * cd /path/to/ai-digest-bot && venv/bin/python cli.py fetch >> logs/fetch.log 2>&1

# проверить, не нажал ли админ кнопку одобрения — каждую минуту
* * * * * cd /path/to/ai-digest-bot && venv/bin/python cli.py moderate >> logs/moderate.log 2>&1

# опубликовать по слотам — время слотов совпадает с posting.slots в config.yaml
0 10,14,19 * * * cd /path/to/ai-digest-bot && venv/bin/python cli.py publish >> logs/publish.log 2>&1

# снять рекламные посты, которым пора выйти — раз в час
0 * * * * cd /path/to/ai-digest-bot && venv/bin/python cli.py ads-check >> logs/ads.log 2>&1

# снять статистику подписчиков — раз в день
0 3 * * * cd /path/to/ai-digest-bot && venv/bin/python cli.py collect-metrics >> logs/metrics.log 2>&1

# недельный отчёт в админ-чат — по понедельникам утром
0 9 * * 1 cd /path/to/ai-digest-bot && venv/bin/python cli.py weekly-report >> logs/report.log 2>&1
```

Если поменяете `posting.slots` в config.yaml — поменяйте и время в crontab,
они не связаны автоматически (см. «Ограничения» ниже).

## Автозапуск на Windows (Планировщик заданий)

```bat
scripts\install_tasks.bat
```

Двойной клик (сам запросит права администратора) создаёт в Планировщике папку
`\AIDigestBot` с шестью задачами: `fetch` (каждые 30 мин), `moderate` (каждую
минуту), `publish` (в слоты из `config.yaml → posting.slots`), `ads-check`
(раз в час), `collect-metrics` (раз в день в 23:50, внутри — `sync-tracker`) и
`weekly-report` (понедельник 09:00). Задачи идут от вашей учётной записи без
окон и переживают перезагрузку; логи — `logs\<команда>.log`.

Поменяли `posting.slots` — запустите `install_tasks.bat` ещё раз, задачи
перезапишутся. Удалить всё: `scripts\install_tasks.bat /uninstall`.
Проверка без установки: `powershell -File scripts\install_tasks.ps1 -DryRun`.

`collect-metrics` стоит на вечер, а не на ночь: строка дня в xlsx пишется один раз,
и «постов опубликовано» должно быть уже финальным для этого дня. Слоты
`posting.slots` считаются по времени Windows — оно должно совпадать с часовым
поясом канала (`channel.timezone`).

## Как это работает по шагам

1. **`fetch`** — скачивает все включённые RSS/Atom-ленты, отбрасывает уже
   виденные ссылки и новости старше `max_item_age_hours`, отсеивает почти
   одинаковые заголовки с разных источников (нечёткое сравнение). Для
   каждой оставшейся новости просит LLM написать пост **только на основе
   переданного текста** — если фактов мало, модель обязана вернуть отказ, а
   не выдумывать. Готовый черновик уходит в админ-чат с тремя кнопками:
   ✅ Опубликовать · ✏️ Правки нужны · ❌ Отклонить.
2. **`moderate`** — читает нажатия кнопок, обновляет статус черновика в БД,
   убирает кнопки с обработанного сообщения. Проверяет `from.id` из
   `admin.allowed_user_ids` — нажатия от посторонних игнорируются.
3. **`publish`** — берёт самый старый одобренный черновик и публикует его в
   канал, с учётом дневного лимита `posting.max_posts_per_day`. Запускайте
   этой командой ровно в слоты публикации (см. crontab выше) — расписание
   задаёт cron, а не код.
4. **`ads-check`** — снимает рекламные посты, которым вышло время
   (`duration_hours` при бронировании, по умолчанию `ads.default_removal_hours`).
5. **`collect-metrics`** — снимает число подписчиков через Bot API и сразу
   запускает `sync-tracker`. Реальные просмотры постов Bot API не отдаёт (см. ниже).
6. **`weekly-report`** — считает и шлёт в админ-чат текстовый отчёт: сколько
   постов вышло, рост подписчиков, реклама и выручка, топ по просмотрам (если
   есть данные).

## Реклама: букинг из командной строки

```bash
venv/bin/python cli.py book-ad \
  --advertiser "Acme Software" \
  --price 150 --currency USD \
  --at "2026-09-25T10:00:00+00:00" \
  --hours 48 \
  --contact "@acme_manager" \
  --erid "2Vtzqv..." \
  --notes "оплата по счёту, скрин перевода в чате"
```

Само размещение (отправка текста поста в канал) сейчас делается программно
через `digest_bot.ads.publish_booked_ad` — под конкретный рекламный пост
проще всего написать свой мини-скрипт на 5 строк, дёргающий эту функцию, или
расширить `cli.py` под ваш процесс продаж. Про маркировку и ERID: поле есть,
хранится, но само оформление через ОРД/маркировку сюда не входит — она
зависит от вашей юрисдикции и площадки (закон о рекламе разный в РФ,
Казахстане, Узбекистане и т.д.).

## Ссылки-приглашения: откуда пришли подписчики

Под каждую закупку рекламы заведите свою ссылку-приглашение и вставьте её в рекламный пост. Когда человек
вступает, Telegram присылает боту событие `chat_member` с этой ссылкой, и бот записывает вступление. Выходы
из канала ссылку не содержат, поэтому уход засчитывается той ссылке, по которой человек вступал (бот помнит его
`user_id`). В итоге по каждой закупке видно: сколько пришло, сколько ушло, сколько осталось и сколько стоит подписчик.

Что нужно:
- бот — **админ канала** с правом «Приглашать пользователей по ссылкам»;
- `moderate` запускается по расписанию (по README — каждую минуту): он получает события вступлений вместе
  с нажатиями кнопок. Telegram хранит необработанные события 24 часа, после этого они теряются;
- события учитываются **с момента первого запуска `moderate` после обновления** (дата видна в панели);
  вступившие раньше по ссылкам не атрибутируются.

Создать ссылку можно в панели (вкладка «Ссылки»: название, цена закупа, текст рекламы с `{link}`,
кнопки «Копировать ссылку» и «Копировать текст», статистика по дням) или из командной строки:

```bash
venv/bin/python cli.py make-link --name "seed_habr_2026-10" --cost 3000 --currency RUB   --text "Дайджест про ИИ без воды. Подписаться: {link}"
venv/bin/python cli.py link-stats
```

В редакторе поста есть выпадающий список «Вставить ссылку-приглашение» — он подставляет `<a href="…">Подписаться</a>`.

Ограничения:
- вступление по `@username` или через поиск, а также по ссылке, которую админ рекламного канала заменил на свою,
  попадает в строку «Не по нашим ссылкам»;
- «Отозвать» отключает ссылку в Telegram (новые вступления по ней прекращаются), статистика остаётся;
- имя ссылки, которое видно админам в Telegram, — первые 32 символа названия, оно не меняется при переименовании в панели;
- в БД хранится `user_id` вступивших (для привязки выхода к ссылке), других данных о них нет.

## Метрики: важное ограничение Bot API

Telegram Bot API **не отдаёт число просмотров** поста в канале — это
принципиальное ограничение платформы, не баг этого кода. Просмотры доступны
только через MTProto-клиента (Telethon/Pyrogram) под обычным
пользовательским аккаунтом. В `digest_bot/metrics.py` есть
`TelethonViewsCollector` — опциональный модуль, выключенный по умолчанию:

```bash
pip install telethon
# впишите TELEGRAM_API_ID и TELEGRAM_API_HASH в .env (my.telegram.org)
# один раз интерактивно авторизуйте сессию:
python3 -c "
from telethon.sync import TelegramClient
c = TelegramClient('data/telethon.session', API_ID, API_HASH)
c.start()
"
```

Используйте для этого отдельный «технический» аккаунт, не основной личный —
автоматизация через MTProto увеличивает риск ограничений на сам аккаунт.
Без этого модуля отчёты и дашборд работают, просто без раздела «топ постов
по просмотрам» и с ARPU, посчитанным грубее.

## Синхронизация с таблицей: `sync-tracker`

```bash
venv/Scripts/python cli.py sync-tracker [--xlsx путь/к/файлу.xlsx]
```

Читает `data/digest.db` и **дописывает** в `tracker/channel_tracker.xlsx`:
- лист «Метрики» — по строке на каждый день из `channel_stats`, которого ещё нет
  в таблице (дата — по часовому поясу канала; подписчики — последний замер дня;
  посты — сколько опубликовано в этот день; охват — среднее по просмотрам, если
  подключён telethon, иначе пусто). Пишутся только колонки A, B, D, E в первой
  свободной строке-заготовке, формулы не трогаются, новые строки не создаются;
- лист «Продажи_рекламы» — новые брони из `ads`. Для защиты от дублей бот ведёт
  служебную колонку **L «ID брони»** — не удаляйте её значения. Статус переносится
  один раз при добавлении строки, дальше его меняете вы (выпадающий список);
- лист «Закупы» не затрагивается.

Синхронизация идемпотентна. Если файл открыт в Excel, сохранение не удастся —
команда завершится с ошибкой, данные останутся в БД и попадут в таблицу при
следующем запуске. Строки-примеры из шаблона (голубая заливка) бот не трогает
и не удаляет — удалите их сами, когда заведёте реальные данные (они влияют на
Дашборд).

## Таблица-трекер

`tracker/channel_tracker.xlsx` — открывайте в Excel/Google Sheets. Четыре
листа:
- **Метрики** — дата, подписчики, прирост, посты, охват, ERR%.
- **Закупы** — реклама, которую покупаете вы (посевы, Ads), с ценой подписчика
  и окупаемостью в месяцах.
- **Продажи_рекламы** — реклама, которую продаёте вы, с CPM и статусом.
- **Дашборд** — сводка формулами: подписчики, выручка, расходы, баланс, ARPU.

Синий текст — вписываете вы, чёрный — формула (не трогать). Единственная
ручная ячейка на Дашборде — B13, «сколько месяцев отслеживаете». Перегенерить
таблицу с нуля: `python3 tracker/build_tracker.py` (файл создаётся в текущей папке).

## Веб-панель (React + Docker)

Панель показывает метрики канала и управляет постами: подписчики (сейчас, +1/7/30 дней),
подписки и отписки по дням, публикации по дням; список всех постов с поиском и фильтром по
статусу, создание, правка, удаление, смена статуса (одобрить / отклонить / вернуть в черновики).

```bash
# в .env добавьте ADMIN_PASSWORD (без него панель не запустится):  openssl rand -base64 18
docker compose up -d --build
# откройте http://127.0.0.1:8080
```

Один образ: React собирается на первом этапе, FastAPI раздаёт его и API. Панель читает и пишет ту же
`data/digest.db`, что и cron-задачи бота (SQLite в режиме WAL это допускает), `config.yaml` монтируется
только для чтения, токен и пароль берутся из `.env`. Контейнер работает с read-only файловой системой и без
capabilities.

- **Доступ.** По умолчанию порт открыт только на `127.0.0.1`. С другой машины — SSH-туннель:
  `ssh -L 8080:127.0.0.1:8080 root@сервер`, затем http://127.0.0.1:8080. Чтобы открыть наружу
  (`PANEL_BIND=0.0.0.0`), ставьте перед панелью HTTPS-прокси и включите `COOKIE_SECURE: "1"` в
  `docker-compose.yml`: панель умеет публиковать и удалять посты в канале, а вход защищён только паролем
  (5 неудачных попыток — блокировка на 5 минут, сессия — подписанная HttpOnly-cookie, 7 дней).
- **Посты.** «Опубликовать сейчас» и правка/удаление уже опубликованных постов ходят в Telegram через
  токен бота; без `TELEGRAM_BOT_TOKEN` эти действия отключены. Удаление поста из канала необратимо.
  Удалённая запись остаётся в памяти дедупа, та же новость повторно не предлагается.
  Вручную созданный пост сохраняется черновиком, ставится в очередь (уйдёт в ближайший слот `publish`)
  или публикуется сразу.
- **Подписки и отписки.** Bot API отдаёт только текущее число подписчиков, а не события, поэтому подписки
  и отписки считаются по разнице между соседними замерами `collect-metrics`: рост — подписки, падение —
  отписки. Подписка и отписка внутри одного интервала между замерами взаимно гасятся, так что чем чаще
  замеры, тем точнее картина (например, запускайте `collect-metrics` каждый час). Точные события даёт
  только MTProto (telethon) — в панель они пока не подключены.
- **Разработка.** `cd frontend && npm install && npm run dev` (проксирует `/api` на `127.0.0.1:8080`) и
  `ADMIN_PASSWORD=... uvicorn --factory digest_web.app:create_app --port 8080`.

## Известные ограничения / что не автоматизировано

- **Оценка качества черновика** — сознательно ручная (кнопки одобрения).
- **Расписание слотов** — задаётся в crontab, а не читается из
  `config.yaml` кодом; если меняете `posting.slots`, поменяйте и crontab.
- **Реальные просмотры** — нужен отдельный опциональный модуль (см. выше).
- **Маркировка рекламы (ERID/ОРД)** — поле есть, оформление — нет, это
  внешний процесс, зависящий от юрисдикции.
- **Мульти-канал** — на один запуск `config.yaml` = один канал. Для второго
  канала (например, «вакансии/удалёнка» — вторая ниша из вашего плана)
  заведите вторую копию проекта с отдельным `config.yaml` и `data/digest.db`.

## Безопасность

`.env` не должен попасть в git или публичный чат — там токен бота и ключ
API. `config.yaml` можно коммитить, секретов там нет по дизайну (они читаются
только из окружения).
